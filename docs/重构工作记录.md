# 重构工作记录 —— 机器人"能量机关"固件

这份记录尽量写给没做过嵌入式的人看，所以只讲"原来哪儿不好、现在怎么分工、修好了哪些事"，
技术细节都指向文末的文档索引。

先说这是个什么东西。能量机关是赛场上一个会转的装置：中间一块主板（下面叫**主机**）负责转动、
发指令、显示状态；外围五块会发光的灯板（下面叫**从机**）是被打的目标。规则要求主机按节奏点亮
其中一块或一对，队员在限定时间内打中它，才算激活成功。这次重构做的是这两类板子上跑的程序，
硬件沿用 2025 赛季那块板，没有改动。

老程序能跑完一场，但没人敢改：改一处要通读整个文件，出问题只能靠猜。下面这些是逐行比对老程序
和台架实测后整理出来的具体事实。灯珠驱动那一套核心思路老程序是对的，原样搬了过来，要动的是
它外围的东西。

## 一、为什么要重构

### 1.1 结构上的问题

| 问题 | 老代码里的样子 | 造成的后果 |
|---|---|---|
| 所有事挤在一个文件 | 老主板的程序有 809 行，收指令、判断进度、控制灯、算电机全写在里面 | 改任何一处都要通读全文件，出问题说不清是谁影响了谁 |
| 参数散落，两边还不一样 | 每根线上接了几颗灯、某个动作等多久，散在代码各处；同一根线主板写 88 颗、灯板写 87 颗 | 换板、改线要全文搜数字；两套程序其实驱动的不是同一批灯，从代码上看不出来 |
| 复制过来没删干净 | 灯板工程的代码被复制到主板工程裁剪，留下 4 路灯的代码全在跑，而主板上实测只接了 1 条灯带 | 白白占掉约 38KB 内存，而整块芯片一共只有 128KB；注释和实物对不上，排查被带偏 |
| "进行到哪一步"没有明确记录 | 靠几个"是不是第一次""有没有开始"的开关变量互相覆盖 | 打错、超时、换目标三条路径互相踩，改一处崩三处 |
| 用"死等"的方式等时间 | 程序里直接写"等 0.2 秒"，等的这段时间别的事全停 | 一次等待就是 0.2 秒内所有事件积压 |
| 收指令只留一个位置 | 新指令进来会把还没处理的旧指令挤掉 | 主板要求"先熄灭旧的一对、0.15 秒后点亮新的一对"，灯板只看到后一条 → 旧灯板该熄不熄 |
| 设备之间发的指令没有"信封" | 一条指令 8 个字节，哪个字节是什么意思全靠约定；收到就照做，不校验 | 线路上传输出一个字节出错，就能让整机推进到错误的一轮 |
| 随机数依赖一个已被删掉的定时器 | 每局开场的随机性来自一个每 0.2 秒自增的计数 | 那个定时器没了之后，随机序列可能每局都一样 |
| 灯的亮度值写反了 | 老程序发数据时高低位顺序和灯珠要求相反 | 程序里写亮度 10，实际亮出来像 80；哪天把顺序改对，灯就暗 8 倍 |
| 数组越界 | 主板程序数到第 6 次时读了数组外面的位置 | 小符本该打 5 次，实际打了 6 次，而且这个行为取决于内存里紧挨着放了什么 |
| 五块灯板的编号靠手改一行代码 | 改一行、重新编译、烧进去，没有任何检查，生成的文件名也不带编号 | 五块板共用一个工程，烧错编号等于整场流程错乱，现场极难发现 |

### 1.2 真实暴露的缺陷

老程序当时就记在案的四个问题：

| 编号 | 现象 | 原因 |
|---|---|---|
| ① | 板上的物理开关拨颜色，灯不跟着变，只有开机那一刻算数 | 灯的颜色只在开机时刷一次，后面没人管 |
| ② | 灯跑着跑着花屏、串色 | 程序每一圈都强行重发灯的数据，撞上上一批还没发完的数据 |
| ③ | 灯带末端残点、整条偶发错乱 | 一帧结束后要留一段"空档"告诉灯珠下一帧开始，老代码留的空档刚好卡在及格线上 |
| ④ | 先拨开关再上电，开机颜色会乱 | 读开关和点灯的先后顺序没有约束。这条的回归验证还没做，挂在待办里 |

另外三件也是真事：

- 换目标时旧灯板不熄灭，原因见上表"收指令只留一个位置"。
- 碰一下电极有时被误判成"打错"，导致整局重来。手抖、相邻两块同时碰到，都算不出正确结果。
- 规则要求灯板中部用灯带显示"已经激活了几组"，这个功能老程序从来没实现过。

最后一条不算缺陷但最要命：程序里没有任何能看出"现在内部是什么状态"的东西，查问题只能往代码里
加打印，或者抱一台仪器上台架。

## 二、重构后好在哪里

### 2.1 文件架构：从"一个文件包办"改成四层分工

```
                     2027_Embedded_Buff/
      ┌──────────────────────────┴──────────────────────────┐
      │                                                  │
  主机工程（中心板，会转）                    从机工程（打符灯板 ×5）

  两个工程同构，都按下面四层组织，依赖只准向下：

  ┌─ Core/ ──────────────────────────────────────────────────────
  │    芯片厂商工具自动生成的代码，原则上不手改；只在标了
  │    USER CODE 的空档里放初始化入口和"节拍器"
  │
  ├─ application/ ───────────────────────────────────────────────
  │    业务层：进度怎么推进、被打中算第几环、灯该显示成什么样子
  │
  ├─ bsp/ ───────────────────────────────────────────────────────
  │    硬件层：怎么把数据发给灯珠、怎么收发指令、怎么读开关
  │
  └─ config/ ────────────────────────────────────────────────────
       只放"数"：延时多久、几颗灯、哪根线接什么、规则开关

  业务层可以叫硬件层干活，硬件层不知道业务是什么。要是业务层绕过
  硬件层直接去改芯片底层的设置，这层分工就白做了。
```

好处很实在：某个东西出问题，按"配置 → 硬件 → 业务"三个同名文件一条线查完，不用翻别的文件。
比如灯不亮，只看这三处：这条线接没接、几颗灯（配置层），数据发没发出去（硬件层），要显示什么
图案（业务层）。

文件清单（从机与主机同构，差异写在行末）：

```
2027_Embedded_Buff/
├── 2027_Embedded_Buff_Master/     主机（中心板）
│   ├── config/
│   │   ├── config_board.h         节拍、板上开关的含义     从机多一项：本板编号(1~5)
│   │   ├── config_ws2812.h        灯带：哪根线、几颗灯     从机：六根线各自的灯数
│   │   ├── config_can.h           两条线路的编号、队列长度
│   │   ├── config_buff.h          规则时序与开关          从机多一项：击打消抖窗口
│   │   ├── config_light.h         灯效参数                从机：靶面/环数/箭头对照表
│   │   └── config_motor.h         电机转速与圈数          从机无电机，此文件已删
│   ├── bsp/
│   │   ├── bsp_ws2812.c           把数据发给灯珠
│   │   ├── bsp_can.c              两条线路的收发
│   │   ├── bsp_switch.c           读板上的物理开关
│   │   └── bsp_rng.c              取芯片自带的随机数
│   ├── application/
│   │   ├── buff.c                 大小符流程 + 与灯板通信   从机：收指令 + 本板流程状态
│   │   ├── light.c                中心灯带显示什么         从机：本板灯带显示什么图案
│   │   └── motor.c                让中心板按节奏转起来     从机换成 hit_detect.c
│   └── MDK-ARM/                   编译配置
│
└── 2027_Embedded_Buff_Slave/      从机（打符灯板 ×5），目录结构与主机一致
    └── application/hit_detect.c   哪块被打中、算第几环（仅从机有）
```

### 2.2 把"死等"换成节拍器

老代码靠"等 0.2 秒"这种写法安排节奏；现在只有一个每 1 毫秒走一次的节拍，所有事情按固定档位做：

```
每 1 毫秒    收一遍总线指令（一条都不落下）、给各个步骤计时
每 20 毫秒   看一眼板上的开关（顺手把抖动的杂散信号滤掉）
每 250 毫秒  刷新一次灯效、处理"这一板被打中了"这件事
主循环       空转，什么都不做
```

这一条直接解决了"旧灯板该熄不熄"：主板发"熄灭"和发"点亮"中间只隔 0.15 秒，老灯板程序要 0.2 秒
才看一次指令，只看得到后一条；现在每 1 毫秒看一次，两条都收得到。

### 2.3 状态能看见，台架不用抱仪器

程序内部现在有一组专门用来看的变量：当前进行到哪一步、第几轮、收到几条指令、哪块板被打中算成
第几环、线路上丢了几帧。烧进板子后用调试器直接读这些数，不用加打印。台架方法因此定成一句话：
眼睛看灯，调试器看变量，不需要昂贵的总线分析仪。

自检也做成了开关：打开以后上电就把每条灯带逐个点亮成白色，同时能读出"现在亮的是第几条"，几分钟
就能把"哪根线接的是哪条灯带"核对完。主板就是靠这个方法发现板上印的字和实际接线不一致——印着
"中心圆环"的那个口其实是空的，中心灯带在另一个口上。

### 2.4 规则参数变成开关，不用读代码就能改

哪些是规则定的、哪些是我们自己要试的，全部抽成有名字的开关：小符要打 5 次还是照老程序打 6 次、
第一块要不要计时、熄灭到点亮之间留多少时间、多大范围内的两次触碰算一次、大符没人打时多久换一对
目标。赛前裁判对某条规则有不同理解，改一行重新编译就行，不用碰逻辑。

### 2.5 已经解决的具体问题

| 问题 | 怎么修的 | 拿什么确认修好了 |
|---|---|---|
| 拨开关灯不变色（老 bug①） | 每 250 毫秒比一次开关，变了就立刻重刷 | 台架拨一下看灯是否即时变 |
| 每圈强发导致花屏（老 bug②） | 只有内容真的变了的那条灯带才发，一次节拍最多发两条 | 连续跑半小时、两小时不花屏 |
| 帧尾空档太短（老 bug③） | 空档从"勉强及格"加到约两倍余量 | 用仪器量过波形 |
| 旧灯板该熄不熄 | 灯板程序改成每 1 毫秒收指令、逐条处理；再加一条兜底：换目标时，本轮没被点亮的板自己回休眠 | 程序里有个计数专门记"曾经丢过熄灭帧"，正常应一直为 0 |
| 三块板同时亮（实测） | 同上兜底：把"该亮的这一对"当成唯一依据，不在里面的板自己灭 | 换轮后全场只应有两块亮 |
| 大符打中的那块看不出已经打完 | 大符下打中的板灯臂立刻熄灭（小符保持原来的常亮效果） | 实机看 |
| 打过的板熄灭后再也不亮、整机老是整局重来 | 触碰信号是即时记录的，但 0.25 秒后才判定，中间状态可能已经变了；改成"状态一变就作废在途的触碰" | 一个专门的计数：只有真打错才会涨 |
| 碰一下误判打错 | 只认一个方向的信号，加 100 毫秒消抖窗，不在名单上的信号只计数不判定 | 被消抖吞掉的次数、杂散次数分开统计 |
| 随机数每局可能重复 | 改用芯片自带的随机源，开机取一次 | — |
| 大符随机点到同一对灯板两遍 | 五块板两两配对共 10 种，改成从中不重复地取。老做法实测相邻两轮撞对的概率 10%，一局平均撞 0.91 次 | 取 20 万局模拟：撞对 0 次 |
| 大符没人打就一直亮着同一对 | 每 2.5 秒没人打就换一对继续，不算失败、进度不退、也不整局重来 | 一个"换了几次"的计数在涨，而轮次不变 |
| 小符实际打 6 次（数组越界导致） | 默认按规则 5 次；想复刻老行为改一个开关，越界读换成有定义的行为 | — |
| 线路断了程序卡死 | 发送前先查有没有空位，满了就丢并记一笔，绝不等待 | 断线时丢包计数涨、程序不死 |
| 空着的灯带白占内存 | 没接灯带的通道不分配内存、不发送 | 编译产物核对，腾出约 38KB |
| 五块板编号容易烧错 | 编号超出范围直接编译不通过；输出文件名带板号；烧录纪律写进测试指南 | 联机前逐块核对 |

### 2.6 新增的能力

从机的完整灯效库。待激活是靶面 19 段亮起加箭头流动，已激活按环数点亮对应段位，
全激活填上下两条灯带。所有对照表与 2025 的灯板程序逐条核对后继承，硬件没变，不需要重新标定。

大符的两条新规则：一轮里点过的灯板对不重样；没人打就每 2.5 秒换一对目标。

进度链路已经打通：主机每帧都带"已经激活了几组"，灯板也收到了。但灯板中部把这几组显示出来的
画法还没做，排在台架验收全绿之后。

一套台架验收方法：把验收拆成五组按顺序做（收指令、击打判定、全流程、灯效亮度、五板联机与长时间
运行），每组给步骤、判据、记录表，最后附一张"看到什么现象先看哪个变量"的排查表。

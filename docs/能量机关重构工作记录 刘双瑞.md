# 能量机关重构工作记录 

> 刘双瑞 2026.10.17

能量机关构成：中间一块主板（下面叫**主机**）负责转动、发指令、显示状态；外围五块会发光的灯板（下面叫**从机**）是被击打的目标。规则要求主机按节奏点亮其中一块或一对，在限定时间内打中它才算激活成功。

硬件沿用 2025 赛季的，本次重构仅针对嵌入式软件。

---

## 一、为什么要重构

### 1.1 最直观的一处：`main()` 之前 98 行全是变量定义

老主板程序的 `main()` 从第 166 行才开始，在此之前的第 63~160 行是一整段全局变量定义：
73 行有效代码、68 条声明、59 个全局变量；灯板程序同样有 52 行（37 条声明、25 个变量）。
下面照录老文件（行号为原行号，中间省略若干行）：

这段清单本身不影响机器运行，但是：

- 名字无法表意。`a`、`b`、`w`、`t`、`dt`、`i`、`ii`、`temp`、`adada` 共 9 个，含义只能靠
  读它被使用的那几行反推；`adada` 定义之后没有任何地方用到。
- 同一件事有多个说法。表示"当前处于哪一步"的变量有 `Buff_Status`、`BUFF_State`、`state`、
  `last_state`、`BUFF_TYPE` 五个，加上名字里带 flag 的一类共 14 个，彼此之间没有任何约束；
  第 111 行 `state = 1` 里的 1 代表什么，要翻到使用它的地方才知道。
- 任何函数都能改。这些变量是全局的，程序运行到某一步时它的值被谁改过，只能逐行排查。
- 与实物不符。第 64~67 行声明了 4 个灯带数组，而主板上实测只接了 1 条灯带；第 116~118 行
  三个数组的注释只写了"小符灯臂""大符灯臂"，其中 `num` 在数到第 6 次时会读到数组之外
  （见 1.2）。

新程序把这类数值全部收进 `config/` 目录的六个头文件，每条都注明单位与取值范围，表示进度的
状态改用有名字的枚举，观察量单独命名（见 2.1 与 2.4）。

### 1.2 结构上的问题

| 问题 | 老代码的情况 | 造成的后果 |
|---|---|---|
| 职责集中在单一文件 | 老主板程序 809 行，通信解析、进度判定、灯带控制、电机运算写在同一文件内 | 修改任一功能都要通读全文件，故障责任也难以界定 |
| 参数分散，两侧不一致 | 灯珠数量、时间参数、引脚定义散落在代码各处；同一引脚主板记 88 颗、灯板记 87 颗 | 换板或改线要全文检索数字；两套程序实际驱动的并非同一批灯带，从代码上看不出来 |
| 复制残留未清理 | 灯板工程复制到主板工程后裁剪不彻底，保留 4 路灯带的初始化与发送，而主板实测只接 1 条 | 占用约 38KB 内存（芯片总量 128KB）；注释与实物不符，干扰排查方向 |
| 轮次状态没有显式定义 | 用"是否第一次""是否已开始"等若干标志位相互覆盖来表达当前步骤 | 击打错误、超时、更换目标三条路径相互覆盖，修改的影响面无法控制 |
| 阻塞式延时 | 主循环中直接调用 0.2 秒等待，期间其余任务全部停止 | 单次等待造成 0.2 秒的事件积压 |
| 指令接收是单缓冲 | 新指令覆盖尚未处理的旧指令 | 主板"熄灭旧对"与"点亮新对"相隔 0.15 秒，灯板只能收到后一条，旧灯板无法熄灭 |
| 通信没有校验 | 一条指令 8 个字节，字段含义只靠约定，收到即执行 | 线路传输出错一个字节，就能让整机推进到错误的轮次 |
| 随机数依赖已被删除的定时器 | 每局的随机性来自一个每 0.2 秒自增的计数 | 该定时器取消后，随机序列可能每局相同 |
| 灯珠数据的位序相反 | 移位顺序与灯珠要求相反，低位先发 | 程序中的亮度值 10 实际表现为 80；位序改对后亮度下降 8 倍，需重新定值 |
| 数组越界访问 | 计数到第 6 次时读取了数组之外的内存 | 小符实际需击打 6 次（规则为 5 次），且结果取决于内存布局 |
| 灯板编号没有校验 | 五块灯板靠手改一行宏定义区分，无范围检查，输出文件名不含编号 | 编号烧错导致整场流程错乱，现场难以定位 |

### 1.3 真实暴露的缺陷

老程序当时记在案的四个问题：

| 编号 | 现象 | 原因 |
|---|---|---|
| ① | 拨动开关切换颜色，灯不随之改变，只在上电时生效一次 | 灯色只在上电流程中写入，运行期间没有刷新 |
| ② | 运行中出现花屏、串色 | 每一圈都无条件重新启动 5 路发送，与上一批尚未发完的数据冲突 |
| ③ | 灯带末端有残点、整条偶发错乱 | 帧与帧之间的空档过短，约 62.5µs，只略高于 50µs 的规格下限 |
| ④ | 先改开关再上电，中心灯带颜色异常 | 开关读取与灯带初始化的先后关系没有约束；该项回归验证尚未完成 |

另外三项同样是实测确认的：

- 更换目标时旧灯板不熄灭，原因见 1.2 的"指令接收是单缓冲"。
- 电极触碰被误判为"打错"并导致整局重来：开关抖动、相邻电极同时被碰到，都得不到正确判定。
- 规则要求灯板中部用灯带显示已激活的组数，这个功能老程序没有实现。

## 二、重构后

### 2.1 文件架构：单一文件改为四层分工

```
                     2027_Embedded_Buff/
      ┌──────────────────────────┴──────────────────────────┐
      │                                                     │
  主机工程（中心板）                              从机工程（灯板 ×5）

  两个工程结构相同，都按下面四层组织，依赖只准向下：

  ┌─ Core/ ──────────────────────────────────────────────────────
  │    芯片厂商工具自动生成的代码，原则上不手改；只在标注
  │    USER CODE 的空档内放初始化入口与时间节拍
  │
  ├─ application/ ───────────────────────────────────────────────
  │    业务层：轮次推进、击打环数判定、灯效显示
  │
  ├─ bsp/ ───────────────────────────────────────────────────────
  │    硬件层：灯珠数据发送、指令收发、开关读取、随机数
  │
  └─ config/ ────────────────────────────────────────────────────
       配置层：只有数值——时间参数、灯珠数量、引脚映射、规则开关

  业务层调用硬件层，硬件层不了解业务；若业务层越过硬件层直接
  修改芯片底层设置，分层即失去意义。
```

分层的直接收益是定位路径固定：某一外设出问题，按配置层、硬件层、业务层三个同名文件顺序检查即可。
以灯不亮为例，只需查三处——该引脚是否接线、灯珠数量（配置层），数据是否发出（硬件层），应显示的
图案（业务层）。

文件清单（从机与主机同构，差异标注在行末）：

```
2027_Embedded_Buff/
├── 2027_Embedded_Buff_Master/     主机（中心板）
│   ├── config/
│   │   ├── config_board.h         节拍与开关定义         从机增加本板编号(1~5)
│   │   ├── config_ws2812.h        灯带引脚与灯珠数量      从机：六个通道的灯珠数量
│   │   ├── config_can.h           两条总线的标识与队列长度
│   │   ├── config_buff.h          规则时序与开关         从机增加击打消抖窗口
│   │   ├── config_light.h         灯效参数              从机：靶面/环数/箭头对照表
│   │   └── config_motor.h         电机转速与圈数         从机无电机，文件已删
│   ├── bsp/
│   │   ├── bsp_ws2812.c           灯珠数据发送
│   │   ├── bsp_can.c              两条总线收发
│   │   ├── bsp_switch.c           读取板上开关
│   │   └── bsp_rng.c              硬件随机数
│   ├── application/
│   │   ├── buff.c                 大小符流程与通信协议    从机：指令接收与本板轮次状态
│   │   ├── light.c                中心灯带显示           从机：本板灯效
│   │   └── motor.c                中心板转动控制         从机替换为 hit_detect.c
│   └── MDK-ARM/                   编译配置
│
└── 2027_Embedded_Buff_Slave/      从机（灯板 ×5），目录结构与主机一致
    └── application/hit_detect.c   击打位置与环数判定（仅从机有）
```

### 2.2 时间调度：由阻塞等待改为统一节拍

老程序用固定等待安排节奏；新程序只有一个每 1 毫秒触发一次的节拍，其余任务按分频执行：

```
每 1 毫秒    接收总线指令（逐条处理，不覆盖）、为各步骤计时
每 20 毫秒   读取板上开关（同时滤除抖动产生的杂散信号）
每 250 毫秒  刷新灯效、处理击打事件
主循环       空转，不执行任务
```

这一改动同时解决了旧灯板不熄灭的问题：主板发出"熄灭"与"点亮"两条指令相隔 0.15 秒，老灯板每
0.2 秒查看一次，只能看到后一条；改为每 1 毫秒查看后，两条均能收到。

### 2.3 运行状态可观测

程序内部保留一组只供观察的变量：当前步骤、轮次、累计接收指令数、击打位置与环数、通信丢帧数。
调试时用仿真器直接读取，不必在代码里加打印。台架检查因此简化为两项：观察灯效、读取观察变量，
不再需要总线分析仪。

自检同样做成编译期开关：开启后上电即逐条把灯带点亮为白色，并输出当前点亮的通道序号，可在几分钟
内完成引脚与灯带对应关系的核对。主板正是用这一方法确认了板面丝印与实际接线不一致——标注"中心
圆环"的接口并未接线，中心灯带实际在另一个接口上。

### 2.4 规则参数集中为开关

与规则相关的可调项全部提取为具名开关：小符击打次数（5 次为规则值，6 次为老程序行为）、首组是否
计时、熄灭与点亮之间的间隔、两次触碰合并计为一次的时间窗、大符无击打时更换目标的周期。赛前若
裁判对某条规则另有解释，修改对应开关重新编译即可，不涉及逻辑改动。

### 2.5 已经解决的问题

| 问题 | 处理方式 | 确认依据 |
|---|---|---|
| 拨开关后灯不变色（老 bug①） | 每 250 毫秒比对一次开关，有变化立即重刷 | 台架拨动开关，灯即时变化 |
| 每圈强制重发导致花屏（老 bug②） | 只有内容确实变化的那条灯带才发送，单个节拍最多发两条 | 连续运行半小时、两小时无花屏 |
| 帧间空档过短（老 bug③） | 空档由约 62.5µs 增加到约 112µs | 逻辑分析仪实测波形 |
| 旧灯板该熄不熄 | 灯板改为每 1 毫秒接收并逐条处理；另加兜底：更换目标时，本轮未被点亮的灯板自行回到休眠 | 程序内设有"曾经丢失熄灭帧"的计数，正常应始终为 0 |
| 三块灯板同时亮（实测） | 同上兜底：以"本轮该亮的这一对"为唯一依据，不在其中的灯板自行熄灭 | 轮次切换后全场只有两块亮 |
| 大符中被击打的灯板看不出已经打完 | 大符下被击打的灯板灯臂立即熄灭；小符保持原有的常亮效果 | 实机观察 |
| 被击打过的灯板熄灭后不再点亮，整机反复整局重来 | 触碰信号即时记录、0.25 秒后才判定，期间轮次状态可能已经改变；改为状态一变即作废在途的触碰 | 专用计数仅在真正打错时才增加 |
| 触碰被误判为打错 | 只识别单一方向的信号，增加 100 毫秒消抖窗，不在名单内的信号只计数不判定 | 消抖吞掉的次数与杂散次数分别统计 |
| 随机数每局可能重复 | 改用芯片自带随机源，上电取一次种子 | — |
| 大符重复点亮同一对灯板 | 五块灯板两两组合共 10 种，改为不重复地依次取用。老做法实测相邻两轮重复概率 10%，一局平均重复 0.91 次 | 20 万局模拟：重复 0 次 |
| 大符无击打时一直亮着同一对 | 每 2.5 秒无击打即更换一对目标，不计为失败、进度不回退、也不整局重来 | 更换次数计数递增，轮次保持不变 |
| 小符实际击打 6 次 | 默认按规则取 5 次；如需复现老程序行为改一个开关，越界读取换成明确定义的行为 | — |
| 总线断开时程序卡死 | 发送前先查空位，无空位即丢弃并计数，不做等待 | 断线时丢包计数增加而程序不死 |
| 未接灯带的通道占用内存 | 该通道不分配内存、不发送 | 编译产物核对，释放约 38KB |
| 五块灯板编号容易烧错 | 编号越界直接编译不通过；输出文件名带编号；烧录纪律写入测试指南 | 联机前逐块核对 |

### 2.6 新增内容

灯板侧的完整灯效：待激活为靶面 19 段加流动箭头，已激活按环数点亮对应段位（含 1 环点亮六段的
情况），全激活点亮上下两条灯带。全部对照表与 2025 灯板程序逐条核对后继承，硬件未变，无需重新
标定。

大符的两条新规则：同一局内点亮的灯板对不重复；无击打时每 2.5 秒更换一对目标。
